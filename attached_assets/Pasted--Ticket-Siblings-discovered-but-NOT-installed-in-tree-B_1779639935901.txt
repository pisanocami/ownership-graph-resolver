# Ticket: Siblings discovered but NOT installed in tree

**Bug ID:** ISSUE-AWARA-SIBLINGS-MISSING
**Severity:** HIGH — silently corrupts brief output, makes runs non-reproducible
**Component:** ownership phase → siblings slot population
**Reproducible:** YES (run any small brand within Resident Home LLC as focal)

-----

## Bug summary

The ownership phase **discovers siblings via search** but **fails to install them in the tree’s `siblings[]` slot**. The reasoning string of the focal entity mentions them, but the structured slot is empty.

Downstream consequence: revenue phase only processes installed entities, so siblings never get revenue estimates, sibling ranking shows “No siblings”, brief generates with 0 siblings.

-----

## Reproduction case

### Setup A — works correctly

- Focal: **Nectar Sleep**
- Parent: Resident Home LLC
- Date: 2026-05-24
- Result: 4 siblings captured (DreamCloud $300M, Awara $60M, Siena $65M, Cloverlane —)
- Events count: 86
- Revenue phase entities: 7

### Setup B — fails

- Focal: **Awara Sleep**
- Parent: Resident Home LLC (same)
- Date: 2026-05-24 (~3h later)
- Result: “No siblings”
- Events count: 57
- Revenue phase entities: 3 (focal + parent + grandparent only)

**Same parent. Different focal. Opposite sibling capture behavior.**

## Hypothesis: where the bug lives

Most likely in the ownership phase, between:

1. **Sibling discovery** (search queries — log evidence shows this works)
1. **Sibling installation** (populating `tree.siblings[]` array — this fails)

Possible causes (please investigate):

### Hypothesis A — focal-size budget gate

Code may have a heuristic like “if focal revenue estimated < $X, skip expensive sibling enumeration.” If true, the gate is wrong: sibling capture is needed REGARDLESS of focal size, because reconciliation and competitive context depend on it.

### Hypothesis B — sibling enumeration phase gated by ownership_clarity

Code may skip sibling enumeration when `ownership_clarity = "clean"` because chain is short. If true, the gate is wrong: clean chains still benefit from sibling enumeration.

### Hypothesis C — sibling enumeration only runs for “high-attention” focals

Code may have rank-based attention budget: focal with high rank/revenue gets full sibling pass, low-rank focal skips it. If true, the gate is wrong: low-rank focal NEEDS sibling context to be useful (lone $40M brand in conglomerate is meaningless without siblings).

### Hypothesis D — sibling discovery results are computed but discarded

Most likely: search results contain sibling names but the parser only extracts them when there’s an explicit prompt asking “what are the siblings”. When the run is short, that prompt is skipped.

## Proposed fix direction

If hypothesis D is correct (search results contain siblings but parser misses them):

**Add explicit “sibling discovery” sub-step in ownership phase:**

```
After parent identification:
  1. Search "[parent] portfolio brands" (1-2 queries)
  2. Search "[parent] subsidiary brands [segment]" (1 query)
  3. Parse all results for brand names + categorization
  4. Install discovered brands into tree.siblings[] BEFORE proceeding to revenue phase
  5. Minimum guarantee: if parent revenue > $100M and parent has multiple
     brands in public references, install at least 3 siblings
```

Cost: 2-3 additional search queries per run when parent is conglomerate. Worth it.
